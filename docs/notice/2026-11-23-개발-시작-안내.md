## 3. 백엔드

### 3-1. 패키지 구조 (07_cicd 와 같은 계층별 구조)

07_cicd 처럼 **계층(역할)별**로 패키지를 나눕니다. 지금 `dev` 에 있는 기능별 패키지(`auth/`, `inventory/` …)는 구조 정리 PR 에서 아래처럼 바꿉니다.

```
backend/src/main/java/com/nansogong/
├── NansogongApplication.java
├── common/        설정 · 보안 · 공통 처리 (이미 있음)
│                  SecurityConfig, WebConfig, SwaggerConfig, ExternalApiConfig,
│                  AppProperties, SchedulingConfig, PingController
│                  + GlobalExceptionHandler (새로 추가)
├── controller/    URL 을 받아 service 를 부른다          InventoryController
├── service/       업무 규칙 · 계산 · 트랜잭션             InventoryService
├── repository/    JPA Repository                       InventoryItemRepository
├── model/         @Entity                              InventoryItem
├── dto/           요청 · 응답 record                    InventoryItemCreateRequest, InventoryItemResponse
├── exception/     업무 예외                             BusinessException(기반), InventoryItemNotFoundException
└── ai/            Spring AI (ChatClient 설정, @Tool 도구 클래스)

backend/src/main/resources/
├── application.yml
├── db/migration/  Flyway SQL (이미 있음)
└── prompts/       AI 시스템 프롬프트 파일 (*.st)       07_cicd 와 같음
```

**파일 이름 규칙**: 클래스 이름 앞에 **도메인 이름**을 붙입니다. 같은 폴더를 여러 명이 같이 쓰지만 파일은 겹치지 않으므로 Git 충돌이 거의 나지 않습니다.

| 도메인 | 클래스 이름 앞부분 | URL |
|---|---|---|
| 회원 · 인증 | `Auth…`, `Member…` | `/api/auth/**`, `/api/me` |
| 매장 | `Store…` | `/api/stores/**` |
| 연동 | `Integration…`, `Pos…` | `/api/stores/{storeId}/integrations/**` |
| 날씨 | `Weather…` | `/api/stores/{storeId}/weather` |
| 홈 | `Home…` | `/api/stores/{storeId}/home/**` |
| 쿠폰 | `Coupon…` | `/api/stores/{storeId}/coupons/**` |
| 재고 | `Inventory…` | `/api/stores/{storeId}/inventory-items/**` |
| 발주 | `Purchase…` | `/api/stores/{storeId}/purchase-orders/**` |
| 메뉴 | `Menu…` | `/api/stores/{storeId}/menus/**` |
| 매출 · 비용 | `Sales…`, `Expense…` | `/api/stores/{storeId}/sales/**` |
| 에이전트 | `Agent…` | `/api/stores/{storeId}/agent/**` |

> 모든 데이터는 **매장별**로 나뉩니다 (구현-1-6). 그래서 URL 에 `{storeId}` 를 넣습니다. 서비스 맨 앞에서 "이 매장이 토큰 주인의 매장인가?" 를 확인합니다. 07_cicd 의 `checkMine()` 과 같은 방식입니다.

### 3-2. 코드 규칙 (07_cicd 에서 배운 것 그대로)

| 계층 | 규칙 | 07_cicd 예시 |
|---|---|---|
| Controller | 로직 없이 service 호출과 DTO 변환만. 토큰 주인은 `@AuthenticationPrincipal Jwt jwt` → `jwt.getSubject()` | `AccountController` |
| REST | URL 은 명사, 동작은 HTTP 메서드. 생성 `201`, 삭제 `204`, 목록은 `Page<>` | `AccountController` 맨 위 주석 |
| DTO | `record` + `static from(Entity)`. **Entity 를 그대로 응답하지 않는다** | `AccountResponse.from()` |
| 검증 | 요청 DTO 에 `@NotNull`, `@Positive` 등 + Controller 에서 `@Valid` | `DepositRequest` |
| Entity | `@Data` 대신 `@Getter`. 값 변경은 setter 대신 **업무 메서드**(`open()`, `close()` 처럼) | `Account.open()` |
| 돈 | `BigDecimal`, `DECIMAL(19,2)`. 0인지 비교할 때는 `compareTo` | `Account.balance` |
| 예외 | 업무 이름으로 된 예외 + `ErrorResponse(code, message)` | `AccountNotFoundException` |
| 로그 | `@Slf4j`, `log.info("… {}", 값)` (문자열을 `+` 로 이어 붙이지 않는다) | `AccountService` |

**예외는 충돌을 줄이려고 07_cicd 에서 한 가지만 바꿉니다.**
07_cicd 는 예외마다 `GlobalExceptionHandler` 에 메서드를 하나씩 추가했습니다. 우리는 5명이 이 파일 하나를 동시에 고치게 되므로, 다음처럼 합니다.

```java
// exception/BusinessException.java (구조 정리 PR 에서 1번만 만든다)
public abstract class BusinessException extends RuntimeException {
    private final HttpStatus status;
    private final String code;
    // 생성자 · getter
}

// exception/InventoryItemNotFoundException.java (각자 만든다)
public class InventoryItemNotFoundException extends BusinessException {
    public InventoryItemNotFoundException(Long id) {
        super(HttpStatus.NOT_FOUND, "INVENTORY_ITEM_NOT_FOUND", "품목을 찾을 수 없습니다: " + id);
    }
}
```

`GlobalExceptionHandler` 는 `BusinessException` 하나만 처리하면 됩니다. 각자는 **예외 클래스만 추가**하고 핸들러 파일은 건드리지 않습니다.

### 3-3. 백엔드 처음 할 일 (각자 자기 도메인)

1. **표 설계 → Flyway SQL**: `V<연월일시분>__create_<표이름>.sql`. 모든 업무 표에 `store_id` (매장 FK) 를 넣는다
   - 🚨 `store` · `member` 표는 다른 표가 모두 참조하므로 **인증 · 매장 담당이 가장 먼저** 올린다. 다른 사람은 그 SQL 이 머지된 뒤 자기 표를 올린다
2. **기능 하나를 끝까지**: model → repository → service → controller → dto. 처음에는 "목록 조회" 처럼 가장 쉬운 것 하나로 한다
3. **확인**: Swagger(`/swagger-ui/index.html`) 또는 `backend/src/api.http` 에 내 요청을 추가해서 확인한다
4. **테스트 1개**: 기능마다 흐름 테스트를 최소 1개 만든다 (07_cicd 의 `TransferFlowTest` 처럼). PR 마다 Actions 가 돌린다 (Testcontainers 라 Docker Desktop 필요)
5. **데모 데이터**: 표가 생기면 `infra/demo-data/` 에 발표용 데이터 SQL 을 추가한다

**인증 · 매장 담당은 우선순위가 다릅니다.** 다른 사람이 Swagger 로 API 를 시험하려면 로그인 토큰과 매장이 필요합니다. 그래서 아래 순서로 먼저 만듭니다.
**① member · store 표 → ② 회원가입 · 로그인(JWT 발급) → ③ 매장 등록 · 내 매장 확인 메서드** (`StoreService.checkOwner(memberId, storeId)` 처럼 다른 사람이 부를 메서드)

### 4-2. 코드 규칙

| 규칙 | 이유 |
|---|---|
| **컴포넌트에서 `fetch` 를 직접 쓰지 않는다.** 항상 `api/<도메인>.js` → `request()` | 토큰 · 에러 처리를 한 곳에서만 고치기 위해 (07_cicd 와 같음) |
| 서버 데이터는 TanStack Query, `queryKey` 에 **`storeId` 를 꼭 넣는다** | 매장을 바꾸면 다른 매장 데이터가 보이는 사고를 막는다 (`store/useStoreSelection.js` 주석) |
| 로그인 토큰은 메모리(Zustand)에만. `localStorage` 금지 | XSS 로 토큰이 털리지 않게 (07_cicd `bank.js` 주석과 같음) |
| 에러는 `err.message` 를 그대로 보여 준다 | 서버의 `ErrorResponse.message` 가 사용자용 문구다 |
| 모바일 우선. 화면 폭 360px 에서 먼저 확인 | PWA · 사장님 휴대폰 (구현-7-3) |
| shadcn 부품 추가(`npx shadcn@latest add …`)는 PR 에 따로 표시 | `components/ui/` 는 공용이라 겹치면 충돌 |

### 4-3. 프론트 처음 할 일

1. **공통 틀 (1명)**: 하단 탭바 `홈 · 재고 · 메뉴 · 매출` + 빈 화면 4개 + 로그인 전/후 전환. 이것이 머지돼야 각자 화면을 끼울 자리가 생긴다
2. **로그인 화면 (인증 담당)**: `api/auth.js` + `store/useAuthStore` 연결. 07_cicd 의 `LoginPage` · `AuthContext` 흐름과 같다
3. **각자**: `api/<도메인>.js` 에 함수 추가 → `components/<도메인>/XxxPage.jsx` 에 화면 하나. 백엔드 API 가 아직 없으면 **가짜 데이터를 return 하는 함수**로 먼저 만들고, API 가 생기면 `request()` 로 바꾼다
4. 환경 확인 화면(`App.jsx` 의 연결 상태 4줄)은 공통 틀 PR 에서 `/dev` 화면으로 옮기거나 지운다

## 6. AI

AI 는 두 갈래입니다. **(1) LLM (Claude) 으로 문구 · 실행 계획을 만드는 것**, **(2) ml/ 의 수요 예측 모델**입니다.

### 6-1. 지켜야 할 원칙 (07_cicd `AiController` 와 같음)

| 원칙 | 내용 |
|---|---|
| 숫자는 코드가, 문장은 AI 가 | 할인 · 원가 · 발주 수량 · 손익 계산은 service 가 한다. AI 는 근거 · 문구만 만든다 |
| AI 는 실패할 수 있다 | `try-catch` 로 감싸고 실패하면 대체값이나 안내 문구를 준다. AI 가 실패해도 기능 자체는 동작해야 한다 |
| AI 의 답을 믿지 않는다 | 정해진 목록 · 스키마에 맞는지 검사한다 (07_cicd: 카테고리가 목록에 있는지 확인). 실행 계획은 JSON 스키마로 받는다 (`.entity(XxxPlan.class)`) |
| 도구는 우리 서버가 실행한다 | Tool Calling 의 도구 클래스는 `memberId` · `storeId` 를 고정해서 만든다. AI 가 다른 매장 번호를 넣을 수 없다 (07_cicd `BankTools`) |
| 개인정보는 보내지 않는다 | 매장 **집계값만** 보낸다. 이름 · 전화번호 · 사업자번호 금지 |
| 프롬프트는 파일로 | `resources/prompts/*.st`. 코드를 고치지 않고 문구만 바꿀 수 있다 |
| 비용 | 개발 중에는 기본 모델(`claude-haiku-5-5`)을 쓴다. 반복 테스트는 단위 테스트에서 AI 를 가짜로 바꿔서(mock) 한다 |

### 6-2. AI 처음 할 일

1. **`ai/` 공통 틀**: `ChatClient` Bean 설정 (`SimpleLoggerAdvisor` 포함), 프롬프트 파일 규칙, 실패 시 대체 규칙 예시 1개
2. **AI 연결 확인 API** (local · dev 전용, 예: `POST /api/ai/ping`). 지금 화면에서는 Claude 연결 여부를 확인할 방법이 없다. ⚠️ 호출할 때마다 요금이 나가므로 `/api/ping` 에 넣지 않는다
3. **에이전트 설계 (agent, 구현-6-x)**:
   - 실행 계획 JSON 스키마 (6-2)
   - 승인 · 보류 · 반려 상태 흐름 (6-3, UF-19)
   - 도구 목록 (6-5): 발주 전송 · 정정 요청 · 쿠폰 역동기화 → 각 도메인 service 를 부르는 `@Tool` 클래스
   - 중복 실행 방지 (6-6, Idempotency-Key)
4. **수요 예측 (구현-6-1)**: `docker compose --profile ml up -d --build` → `ml/notebooks/` 에서 이동평균 baseline 부터 시작. 데이터는 데모 데이터나 목업 POS 판매 데이터를 쓴다. 서비스 연결 방식(A. Python 배치 / B. Java 추론, `ml/README.md`)은 회의에서 정한다
5. **AI 를 쓰는 도메인과 협의**: 메뉴(4-2 레시피 추천, 4-5 신메뉴 추천), 쿠폰(2-6 추천 문구), 홈(2-3 운영 제안). AI 담당이 공통 틀과 사용 예시를 주고, 각 도메인 담당이 자기 프롬프트를 만든다
