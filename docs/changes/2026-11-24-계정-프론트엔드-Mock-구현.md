# 계정·사업자등록·첫 매장 설정 프론트엔드

## 범위와 확인한 기준

- 로그인 → 회원정보·휴대전화 인증 → 사업자등록 → 가입 완료 → 로그인 → 첫 매장 기본정보 또는 홈.
- 저장소의 유저 플로우 1.02 UF-01·02, 요구사항정의서 수정본 1.1, DB 설계 설명 v1.1 및 실제 Flyway SQL을 확인했다. 유저 플로우 1.03과 BPM 원본은 저장소에서 찾지 못했으며, 이번 요청의 흐름을 우선했다.
- 실제 SQL은 `member`·`store`이고, v1.1 설명의 `users`·`stores`에 대응한다. 사업자 1개당 매장 1개를 생성하며 별도 business_registrations 모델은 만들지 않았다.
- 인증 Controller·DTO·HTTP API 명세는 아직 없다. 프론트 내부 모델을 사용하는 개발용 Mock 어댑터를 분리했으며 서버 URL·요청·응답 계약은 확정하지 않았다.
- 백엔드, 홈·재고·메뉴·매출 화면, 기존 수정사항은 유지했다. Git 브랜치 변경·Pull·Merge·Commit·Push를 실행하지 않았다.

## 실행과 개발용 예시

```bash
cd frontend
npm run dev
```

접속: `http://localhost:5173/login`

| 아이디 | 비밀번호 | 로그인 결과 |
|---|---|---|
| demoowner | Owner123! | 기본정보가 있는 매장 → 홈 |
| setupowner | Owner123! | 기본정보가 부족한 매장 → `/onboarding/store` |

가입 화면의 휴대전화 인증번호는 기존 개발 설정과 같은 `000000`이다. 실제 문자 발송이나 본인확인은 하지 않는다. 모든 계정·사업자 확인 화면에 개발용 Mock임을 표시한다.

사업자번호는 아래 예시를 사용한다. 대표자명은 비어 있지 않은 값, 개업일자는 실제 존재하는 `YYYYMMDD` 날짜를 입력한다.

| 사업자번호 | Mock 결과 |
|---|---|
| 1234567890 등 일반 번호 | 정상 예시 |
| 7777777777 | 휴업 |
| 9999999999 | 폐업 |
| 8888888888 | 정보 불일치 |
| 6666666666 | 이미 등록된 사업자 |
| 0000000000 | 조회 불가·신규 사업자 반영 지연 안내 |
| 5555555555 | 첫 요청만 오류, 재시도 시 정상 예시 |

아이디 `retryowner`로 가입하면 첫 최종 가입 요청만 실패한다. 초안과 검증 상태를 유지하고 다시 가입할 수 있다. 정상 예시도 실제 국세청 조회 결과를 의미하지 않는다.

## 상태와 보안 처리

- 아이디·비밀번호 규칙은 미확정이다. 현재 **Mock 임시 규칙**은 아이디 영문 시작 6~50자(영문·숫자·밑줄), 비밀번호 8~64자(영문·숫자·특수문자, 공백 제외)이며 화면에도 임시 규칙이라고 표시한다. 서버 규칙이 확정되면 `utils/auth.js`를 맞춘다.
- 아이디 변경 시 중복 확인을, 이름·휴대전화 변경 시 인증 상태를 초기화한다. 비밀번호 확인은 별도로 검증한다.
- Mock 인증번호 요청은 3분, 인증 증명은 10분 동안 유효하며 잘못된 인증번호 시도 제한도 가상 서버에서 검사한다. 이 시간·제한은 실제 서버 계약이 아니다.
- 사업자등록번호는 화면에서 하이픈을 표시할 수 있지만 어댑터에는 숫자 10자리를 전달한다. 대표자·개업일자·상호를 수정하면 다시 검증해야 한다.
- 사업자 추가·수정·삭제는 최종 가입 전의 메모리 초안이다. 정상 검증을 마친 사업자가 1개 이상 있어야 가입을 요청한다. 입력 중인 사업자를 저장하거나 취소하기 전에는 최종 가입을 막는다.
- Mock은 회원과 모든 매장을 한 번에 생성한다. 실패·중복·검증 만료 시 계정만 먼저 생성하지 않는다. 실제 서버의 원자적 가입 정책은 별도 확인해야 한다.
- 비밀번호·인증번호·인증 토큰·가입 초안을 localStorage, sessionStorage, 라우터 history state에 저장하지 않는다. access token은 기존 Zustand 메모리 저장소를 재사용한다. 가입 성공 시 민감한 초안을 지운다.
- Mock 계정 데이터는 메모리에서만 유지한다. 비밀번호 비교에 쓰는 메모리 해시는 개발 시뮬레이션일 뿐 실제 서버의 비밀번호 저장 구현이 아니다. 새로고침하면 신규 가입 계정과 세션이 초기화된다.
- 로그인 상태 유지 옵션은 서버의 HttpOnly refresh cookie·복구 API가 없으므로 비활성화하고 이유를 표시한다. 클라이언트에서 자동 로그인을 성공한 것처럼 흉내 내지 않는다.
- 로그아웃은 Mock 세션을 무효화하고 인증 정보·선택 매장·가입 초안·Query 캐시를 비운다. 미로그인 보호 경로는 로그인으로 이동한다. 로그인 후 목적지는 매장 기본정보의 완료 여부로 결정한다.
- 기존 업무 화면은 기존 데이터 목업을 계속 사용한다. 이번에 저장한 첫 매장 데이터는 계정·첫 설정 흐름의 Mock에 반영되며, 실제 업무 데이터 연동은 별도 단계다.

## 첫 매장 기본정보

- 필수: 매장명·업종·주소. 상호가 있으면 매장명에 미리 표시한다.
- 선택: 공통 영업시간·정기 휴무일. 영업시간은 휴무일 외 요일에 `{mon: [시작, 마감], ...}` 형태로 적용하며 마감이 빠르면 다음 날 마감을 의미한다.
- 복수 매장은 선택해서 수정할 수 있고, 저장 후 다른 미설정 매장이 있으면 이어서 설정한다. 모두 저장되면 홈으로 이동한다.
- 로그인 후 이동 여부는 매장의 필수 기본정보로 판단한다. POS·품목·초기 재고·레시피·메뉴 연결은 이번 구현 범위가 아니다.

## 백엔드 연결할 기능

아래 함수는 프론트 서비스 경계이며 **HTTP endpoint 또는 확정 DTO가 아니다**. 계약 확정 후 `api/auth.js`, `api/store.js`의 Mock 호출을 기존 `api/client.js`의 `request()` 호출로 교체한다.

| 프론트 함수 | 확인할 서버 계약 |
|---|---|
| checkLoginId | 아이디 정규화·대소문자·길이·중복 판단 |
| requestPhoneCode | 인증 제공자, 요청 식별자, 재전송 간격·만료 |
| verifyPhoneCode | 인증 증명·이름/전화번호 결합·재사용·만료 |
| verifyBusiness | 백엔드 국세청 호출, 정상/휴업/폐업/불일치/조회 불가/중복/오류 구분, 검증 증명 |
| signup | 회원·복수 매장 원자적 생성 또는 단계별 생성 정책, 검증 증명 재검사, 중복·멱등 처리 |
| login / logout | access token·사용자 응답, 서버 토큰 무효화, HttpOnly refresh cookie |
| getCurrentUser / getMyStores | 인증 주체와 소유 매장 목록·초기 설정 상태 |
| updateStoreBasics | 소유권, 매장명·업종·주소·openHours·closedDays 저장 DTO |

추가 확인: 요구사항 1.1은 다른 계정에 등록된 사업자번호도 중복 불가라고 정하지만 현재 SQL의 UNIQUE는 `(member_id, biz_reg_no)`이다. Mock은 요구사항에 따라 다른 계정의 중복도 차단하며, 실제 중복 정책·서버 제약은 백엔드 담당자와 확정해야 한다.
