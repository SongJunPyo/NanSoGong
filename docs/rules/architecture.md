# 아키텍처

**Spring Boot가 업무 · 승인을 관리하고, Python · LangGraph가 AI 작업을 수행하는 구조**입니다. 사용자에게는 하나의 매장 운영 에이전트로 보입니다.

- 이 문서는 **목표 구조**입니다. Python 서비스는 작업 접수 · 워커 · 레시피 초안 흐름부터 만들고 있고, 실행기는 아직 구현되지 않았습니다.
- 쿠팡 로그인과 실제 주문 실행기의 구체적인 구현 방식은 [미정 사항](#미정-사항)으로 남깁니다.
- 실행 방법 · 환경 구성(local / dev / prod) · CI/CD는 [README](../../README.md)에 있습니다.

## 시스템별 역할

| 구성 | 역할 |
|---|---|
| React PWA | 매장 운영 화면, AI 요청, 제안 검토 · 승인, 진행 · 결과 확인 |
| Spring Boot | 사용자 · 매장 권한, 업무 데이터, 발주량 · 원가 계산, 제안 · 승인 · 주문 · 입고 기록 |
| Python / FastAPI | AI 작업 접수 · 조회 · 재개 API, 수요 예측 API |
| Python / LangGraph | 업무별 AI 흐름, 모델 · 도구 호출, 검증 후 수정, 영속 상태 저장 · 중단 · 재개 |
| 브라우저 실행기 | 상품 조회, 옵션 · 수량 선택, 승인된 주문 수행, 외부 결과 확인 |
| PostgreSQL | 업무 기록과 AI 작업 · 체크포인트 저장. 스키마 · 권한을 나눈다 |
| Redis | 기존 인증 · 캐시 등 |
| LangSmith | 민감정보를 뺀 AI 호출 · 도구 사용 · 오류 · 사용량 추적 |

브라우저 실행기는 **사장님 기기에서 실행하는 방향**을 기준으로 검토합니다. 확장 프로그램 · 설치형 앱 같은 구체적인 형태는 아직 정하지 않았습니다.

## 전체 요청 흐름

```mermaid
flowchart TD
    U[사장님 PWA] --> S[Spring Boot<br/>권한 · 업무 데이터 · 계산 · 승인]
    S <--> A[Python FastAPI<br/>작업 접수 · 조회 · 재개 · 예측]
    A --> G[LangGraph 워커<br/>AI 흐름 · 영속 상태]
    G --> C[Claude API]
    G <-->|데이터 · 계산 · 검증 · 결과| S
    S <-.->|명령 · 결과 (방식 미정)| D[브라우저 실행기<br/>사장님 기기]
    S --> DB[(업무 DB)]
    G --> CP[(작업 등록부 · 체크포인트)]
```

그림에서 실행기와의 연결은 논리적인 관계입니다. 명령 전달 · 기기 등록 · 연결 관리 방식은 실행기를 설계할 때 확정합니다.

1. **일반 업무:** PWA → Spring → 도메인 service → DB. Python 장애나 실행기 오프라인이 기본 조회 · 수동 업무를 막지 않는다.
2. **AI 요청:** PWA → Spring 권한 확인 → Python 작업 API (영속 수락) → 워커가 LangGraph 실행.
3. **계산 · 검증:** LangGraph 도구 → Spring 내부 API → 도메인 service. Python은 업무 표를 직접 바꾸지 않는다.
4. **제안:** 그래프 결과 → Spring 검증 · 버전 저장 → 승인 카드.
5. **외부 실행:** 건별 승인 → Spring 승인 · 실행 기록 → 실행 그래프 → Spring을 거쳐 실행기에 명령 → 결과 보고 → Spring 기록.

## Spring과 Python의 경계

Spring은 **업무적으로 맞는지**를, LangGraph는 **어떤 단계를 수행할지**를 맡습니다.

| 상황 | 맡는 곳 |
|---|---|
| 필요 발주량 · 배송비 포함 총액 계산 | Spring |
| 주 거래처 확인 · 허용된 대안 탐색 | LangGraph + 조회 도구 |
| 쿠폰 조건 · 레시피 초안 생성 | Python AI |
| 쿠폰 손익 · 예산 · 재고 충돌 검증 | Spring |
| 검증 실패 내용을 받아 후보 수정 | LangGraph |
| 주문 승인 · 승인 버전 · 매장 소유권 확인 | Spring |
| 인증을 기다렸다가 작업 재개 | LangGraph (재개할 때 Spring이 권한 · 승인 · 조건을 다시 검증) |
| 실제 상품 선택 · 주문 조작 | 브라우저 실행기 |
| 확인된 주문 · 결제 · 입고 결과 저장 | Spring |

## 상태 저장 위치

| 저장 대상 | 관리 위치 |
|---|---|
| 제안 버전 · 승인 범위 · 주문 · 결제 · 입고 | Spring 업무 DB |
| AI 작업의 기준 기록 (매장 · 요청자 · 상태 · 현재 단계 · 보고 순번 · 결과 제안) | Spring 업무 DB `ai_job` ([DB 규칙](db.md#ai-작업-기록-ai_job)) |
| 워커 내부의 작업 접수 · 선점 · 기한 · 전달 이벤트 | Python 영속 작업 등록부 |
| 현재 단계 · 중간 결과 · 반복 횟수 · 재개 위치 | LangGraph 체크포인트 |
| 브라우저 명령 처리 여부 · 현지 실행 상태 | 실행기 쪽 기록 (세부 계약 예정) |

세 저장소를 하나로 묶는 분산 트랜잭션은 없습니다. 복구할 때는 서로 대조합니다 ([AI 규칙 상태 저장 · 재개](ai.md#상태-저장--재개)).

## 수요 예측

```
ml/에서 학습 · 검증
→ 검증된 모델 배포
→ FastAPI가 모델을 불러와 예측
→ Spring이 결과를 검증 · 저장
→ 재고 · 미입고 · 배송 조건을 반영해 발주량 계산
```

- 학습과 예측 서비스를 나눈다. 요청마다 학습하지 않는다.
- 예측 응답에는 모델 버전과 데이터 기준 시각을 넣는다. 예측 판매량을 그대로 최종 발주량으로 쓰지 않는다.
- 실행 방식(Spring 스케줄러가 호출 · 저장) · 입력(날씨 · 특일은 모델 입력이 아님) · 장애 시 처리는 [AI 규칙 수요 예측](ai.md#수요-예측)에 있다.

## 배포 범위

- 지금은 **dev 환경만** 다룬다. 기존 dev EC2 + Docker Compose에 Python API · 워커를 추가하는 방향이다. 운영(prod) 배포 구성은 따로 설계한다.
- 서버에는 브라우저를 두지 않는다.
- Python API · DB · Redis 포트를 인터넷에 공개하지 않는다. 내부 요청에는 서비스 인증과 작업 범위 검증을 적용한다.
- 초기에는 AI 워커 1개, 매장당 실행기 변경 명령 1개로 제한한다. 워커를 늘릴 때 선점 · 만료 · 소유권 설계를 먼저 한다.
- 정기 작업은 Spring `@Scheduled` + ShedLock(Asia/Seoul)으로 시작한다. LangGraph가 스케줄러를 대신하지 않는다.

## 미정 사항

| 항목 | 상태 |
|---|---|
| 실제 웹 조작을 별도 실행기가 담당 | 설계에 반영 |
| 사장님 기기에서 실행 | 기준 방향으로 검토 |
| 확장 프로그램 · Tauri · Electron 등 실행기 형태 | 미정 |
| 쿠팡 최초 로그인 방식 | 미정 |
| 로그인 정보 · 세션의 구체적인 보관 · 재사용 방식 | 미정 |
| 세션 만료 · 재로그인 처리 | 미정 |
| 결제 추가 인증 · 사용자 제어 전환 방식 | 미정 |
| 실제 쿠팡 주문 지원 여부 | 검증 전 |
| Spring ↔ Python 내부 API 경로 · 인증 방식 | 인증 결정: 방향별 토큰 `X-Internal-Token` (Python → Spring `INTERNAL_API_TOKEN`, Spring → Python `AI_SERVICE_TOKEN`). 두 토큰은 **서로 다른 값**을 쓴다 (한쪽이 새어도 반대 방향은 지켜지게). `/internal/**` 는 밖에서 닿지 않게 막는다. 경로: 레시피 초안 4개 확정 (`contracts/recipe-draft/`), 나머지는 기능별 `request` 이슈에서 확정 |
| Python 프로젝트 폴더 · 라이브러리 버전 | 폴더 `ai/` (Python 3.12 · FastAPI, `ai/requirements.txt`). LangGraph · 모델 SDK 버전은 연결 확인 후 고정 |
| 작업 등록부 · 체크포인트 표 구조 | 결정 ([DB 규칙 AI 작업 저장소](db.md#ai-작업-저장소-ai-스키마)) |
| 기기 등록 · 명령 기록 표 구조 | 설계 전 |

서버 작업 흐름에는 인증 필요 · 사용자 개입 · 재개를 이어 붙일 접점만 마련합니다. 실제 로그인 처리와 화면은 인증 방식이 정해진 뒤 구현합니다. 미정 항목을 추측해서 구현하지 않습니다. 결정이 나면 이 표를 고치고, 진행 상황은 GitHub Issue로 관리합니다.

현재 완료 기준은 **목업 쇼핑몰에서 발주 제안 → 건별 승인 → 실행 → 결과 확인이 이어지는 것**입니다. 실제 쿠팡 로그인 · 주문 완료는 따로 검증합니다.
