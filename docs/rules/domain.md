- 표 · 칸 · 타입은 [DB 규칙](db.md)에 있습니다.
- AI가 이 규칙을 어떤 흐름으로 수행하는지는 [AI 규칙](ai.md)에 있습니다.

## 도메인 경계

- 다른 도메인의 repository · Entity를 직접 쓰지 않는다. **그 도메인의 service 메서드(아래 계약)만 부른다.**
- 필요한 메서드가 없으면 다른 도메인 코드를 고치지 않는다. 그 도메인 라벨을 붙인 GitHub Issue로 요청한다 ([이슈 규칙](issue.md)).
- 계약을 바꾸려면 제공하는 도메인과 쓰는 도메인이 모두 확인해야 한다. 바꾼 뒤에는 이 문서와 [DB 규칙](db.md)을 같은 PR에서 고친다.
- `common/` · `frontend/src/api/client.js` 같은 공용 파일은 [AGENTS.md 작업 원칙](../../AGENTS.md#2-작업-원칙)을 따른다.

## 도메인 사이 메서드 계약

| 제공 도메인 | 메서드 | 입력 → 출력 |
|---|---|---|
| 매장 | `StoreService.checkOwner(memberId, storeId)` | 내 매장이 아니면 403 |
| 매출 | `SalesService.saveOrders(storeId, List<PosOrder>)` | POS 주문 저장. 같은 `external_order_id` 는 무시한다 |
| 메뉴 | `MenuService.resolve(storeId, posMenuCode, List<String> optionCodes)` | 코드 → `menuId` 와 옵션별 `menuId` (못 찾으면 null) |
| 메뉴 | `RecipeService.usageOf(menuId, List<OptionQty> options, at)` | **메뉴 1개 기준** 품목별 사용량 `Map<itemId, BigDecimal>` |
| 재고 | `InventoryService.deductForSale(orderItemId)` | `resolve` → `usageOf` × 차감 수량 → 장부 기록 → `deduct_status` 변경 |

- `usageOf` 는 메뉴 1개 기준만 돌려준다. **수량을 곱하는 일은 `deductForSale` 이 맡는다.** 취소 · 부분 취소가 생겨도 `usageOf` 는 바꾸지 않는다.

## 판매 → 재고 차감

1. 옵션 `qty` 는 **잔당** 수량이다. 실제 옵션 수 = `quantity` × `qty` (아메리카노 2잔 + 샷 1 → 샷 2개).
2. 같은 메뉴 · 같은 옵션 조합이면 한 줄로 쓰고 `quantity` 를 늘린다. 옵션이 다르면 다른 줄로 쓴다.
3. 같은 옵션이 두 번 오면 하나로 합치고 `qty` 를 더한다 (샷 + 샷 → `qty: 2`).
4. `amount` = (`unit_price` + `option_price`) × `quantity` − `discount_amount`.
5. 차감 수량 = `quantity` − `canceled_quantity`.
6. 사용량 = Σ(기본 레시피 + 옵션 레시피 × `qty`) × 차감 수량. 단위는 품목의 관리 단위만 쓴다.
7. 메뉴나 옵션 코드가 매핑되지 않았으면 **차감하지 않고 `NEEDS_FIX`** 로 둔다. 매핑에서 '제외'로 정한 옵션(예: 얼음 적게)은 사용량 0으로 정상 처리한다.
8. 취소는 **기존 행을 고치지 않는다.** `canceled_quantity` 를 늘리고 재고 장부에 '취소 환원'을 추가한다.
9. 중복 방지 키는 판매 차감 `SALE:{orderItemId}`, 취소 환원 `CANCEL:{orderItemId}:{누적취소수량}` 이다. 다시 처리해도 한 번만 반영된다.
10. `deduct_status` 는 `PENDING` (저장만 함) → `DONE` (차감 완료) / `NEEDS_FIX` (미매핑 · 레시피 누락 → 연동 · 메뉴 화면에서 보완) / `SKIPPED` (재고를 쓰지 않는 메뉴) 로 바뀐다.

## 재고 계산

1. **추정 재고 = 가장 최근 기준점 수량 + 기준 시각 이후 장부 변동의 합.** 기준점은 `stock_count` 의 최신 행(`counted_at` 순, `INITIAL` 초기 또는 `COUNT` 실사), 변동은 `inventory_transaction.qty_delta` 다. 재고 수량을 칸 하나에 고쳐 쓰지 않고 매번 장부로 계산한다.
2. 시점은 **발생 시각(`occurred_at`)** 으로 판단한다. 반영 시각(`recorded_at`)으로 계산하지 않는다.
3. 기준 시각 **이후(초과)** 에 발생한 변동만 더한다. 기준 시각 이전이나 같은 시각에 발생한 변동은 늦게 들어와도 더하지 않는다. 기준 수량에 이미 포함된 것으로 본다.
4. 기준점이 없으면 추정 재고는 `null`(미설정)이다. 0으로 처리하지 않는다.
5. 계산 결과가 음수여도 0으로 자르지 않는다. 레시피 과다 · 입고 누락의 신호이므로 실사로 바로잡는다.
6. 추정 재고를 실사 수량처럼 보여 주지 않는다. 응답에 기준점 종류 · 기준 시각을 함께 준다.
7. 초기 재고(`INITIAL`)는 **품목당 한 번만** 입력한다. 다시 입력하면 409. 이후 수량 수정은 실사(`COUNT`)로 한다.
8. 초기 재고의 기준 일시는 미래일 수 없고(400), 사용 중지된 품목에는 입력할 수 없다(400).
9. 특정 시각의 추정 재고는 그 시각 이하의 가장 최근 기준점 + (기준 시각 초과 ~ 그 시각 이하) 변동으로 계산한다. 실사 · 폐기를 저장하기 전 미리보기에 쓴다.
10. 실사(`COUNT`)와 폐기 · 손실은 초기 재고가 있어야 등록한다. 없으면 400. 사용 중지 품목 · 미래 시각도 400.
11. 실사 · 폐기 · 손실의 시각은 **가장 최근 기준점보다 뒤**여야 한다. 그 이전 시기의 변동은 기준 수량에 이미 포함돼 계산에 들어가지 않기 때문이다. 이전 시각은 400, 기준점과 같은 시각의 실사는 중복으로 보고 409.
12. 실사를 저장할 때 그 시각의 추정 재고를 서버가 계산해 `estimated_qty` 에 남긴다. 차이 = `counted_qty` − `estimated_qty` (음수면 기록보다 덜 있었다).
13. 폐기 · 손실은 줄어든 양을 양수로 받아 장부에 음수 `qty_delta` 로 기록한다 (`DISPOSAL` · `LOSS`).
14. 폐기 · 손실의 중복 방지 키는 `ADJUST:{Idempotency-Key 헤더}` 다. 같은 키로 다시 보내면 새로 기록하지 않고 처음 기록을 돌려준다. 헤더가 없으면 서버가 키를 만들므로 중복을 막지 못한다.

## 발주 · 구매

1. 예측 · 재고 · 미입고 · 배송 기간으로 **Spring이 필요량을 계산**한다. 데이터가 없는 것(동기화 실패 · 미수신)을 실제 0으로 처리하지 않는다.
2. **주 거래처의 지정 상품부터 확인한다.** 조건이 맞으면 다른 후보를 찾지 않는다.
3. 다음이 **확인됐을 때만** 대안을 찾는다: 품절 · 배송 불가 · 거래 중단 · 설정한 가격 기준 초과. 로그인 만료 · 조회 오류 · 실행기 오프라인은 거래 불가가 아니다. 재인증 · 대기로 처리한다.
4. 대안은 허용 브랜드 · 규격 · 보관 방식 · 납기를 검증한다. 포장 수량을 관리 단위로 바꾼 뒤 **배송비를 포함한 총비용**으로 비교한다.
5. 가격 상승 기준은 같은 거래처의 비교 가능한 상품 이력으로 정한다. 현재 원가를 무조건 기준으로 쓰지 않는다. 대안으로 샀다고 주 거래처를 자동으로 바꾸지 않는다.
6. 상품 · 판매자 · 옵션 · 수량 · 총액 · 배송 조건을 검증한 뒤 버전을 붙여 제안으로 저장한다.
7. **사장님이 주문마다 승인한다.** 소액 · 반복 주문이라도 승인을 건너뛰지 않는다. 한도 · 품목 · 주기만 정하는 포괄 위임은 지원하지 않는다.
8. 실행 직전에 실제 조건을 승인 범위와 다시 비교한다. 다르면 새 제안 버전으로 다시 승인받는다. 승인된 계획과 `approved_scope` 는 덮어쓰지 않는다.
9. 주문은 승인된 상품 · 옵션 · 수량만 처리한다. 장바구니에 있던 무관한 상품을 함께 결제하지 않는다. 승인 뒤 다른 상품으로 바꾸지 않는다. 로그인 세션이 연결됐다고 구매 승인이 된 것은 아니다.

## 주문 · 결제 · 입고 결과

- 주문 접수 · 결제 · 금융 출금 · 비용 인식 · 정상 입고를 **각각 다른 상태로** 구분한다.
- 주문번호나 버튼 클릭만으로 결제 완료라고 판단하지 않는다. **결제 완료를 확인했을 때만** `PAID` 로 바꾸고 `paid_amount` · `paid_at` 을 채운다. 기존 데이터를 확인 없이 `PAID` 로 채우지 않는다.
- 결과가 불명확하면 `CHECKING` 으로 두고 외부 주문 내역부터 조회한다. 재주문 · 다른 거래처로 대체 주문 · 중복 실행을 하지 않는다.
- 일부만 성공했으면 성공한 범위는 보존하고, 실패하거나 불명확한 범위만 처리한다.
- **정상 입고가 확인된 수량만** 재고에 반영한다.
- 대기가 끝나거나 연결이 끊겼다고 이미 보낸 주문이 취소된 것은 아니다.

## 쿠폰

- 쿠폰 조건은 AI가 제안하고, 서버가 예산 · 마진 · 제외 조건 · 재고 · 기존 쿠폰과의 충돌을 검증한다.
- 정해진 횟수 안에서 고쳐도 맞지 않으면 보류한다.
- 사용자 승인 · POS 반영 · 실제 사용은 각각 다른 상태로 관리한다. POS에 중복 등록하지 않는다.
- 쿠폰 발행 방식은 POS 역동기화(승인한 쿠폰을 앱에서 POS로 등록)다. POS 지원 범위는 연동 검증에서 확정한다.

## 메뉴 · 레시피

- AI 레시피는 초안이다. 사용자가 확인하고 추가/저장을 고르면 서버가 품목 · 단위 · 원가를 다시 검증한 뒤 운영 레시피로 반영한다. 별도의 승인 대기는 만들지 않는다.
- 신규 재료 단가처럼 확인되지 않은 수치를 만들어 넣지 않는다.
- 앱에 메뉴를 등록했다고 POS 판매를 시작하거나 자동 발주로 이어가지 않는다.

## 운영 분석

- 서버 집계와 예측 결과를 쓴다. 기준 시각 · 비교 기간 · 출처 · 누락 · 추정 가정을 함께 보여 준다.
- 분석 설명만으로 판매가 · 비용 · 운영 조건을 바꾸지 않는다.
- 관측된 변화를 확정된 인과 효과로 단정하지 않는다. 실제 결과와 사용자 수정 이력은 다음 제안의 참고 자료일 뿐, 효과가 입증됐다는 뜻이 아니다.
- 승인되지 않은 쿠폰 · 메뉴로 예상한 수요는 시나리오로 따로 표시한다. 확정 수요나 구매 허가로 쓰지 않는다.
- 부족한 재료를 더 소모하는 쿠폰은 조정하거나 보류한다.

## 사업자 진위확인

- 가입 화면의 사업자 확인은 사업자번호·대표자명·개업일자 일치와 계속사업자 상태를 함께 확인한다. 불일치·휴업·폐업·조회 실패를 등록 가능으로 처리하지 않는다.
- 최종 가입 시 서버에서 사업자 목록 전체를 재확인하고 회원 1개와 사업자별 매장을 한 트랜잭션으로 저장한다. 중복 아이디·사업자번호, 진위 불일치·휴업·폐업, 인증 증명 오류에는 가입을 거절한다. 사업자번호는 다른 계정에도 중복 등록할 수 없다.
- 회원 인증 도메인은 매장 저장·소유권 검사를 `StoreService`로 호출한다. 주기적인 사업자 상태 갱신은 별도 기능이다.
- API 계약은 [백엔드 규칙](backend.md#국세청-사업자-진위확인), 화면의 연결 범위는 [프론트 규칙](frontend.md#회원가입의-사업자-진위확인)을 따른다.

## 현재 범위 밖

요청이 없으면 만들지 않습니다. 화면이 필요하면 프론트 목업으로 대신합니다. 범위가 바뀌면 이 목록을 같은 PR에서 고칩니다.

| 기능 | 비고 |
|---|---|
| 운영 일정 (`schedule` 표) · 알림 설정 | 화면은 목업만 |
| 콤보 · 세트 메뉴 | 판매로 들어오면 `NEEDS_FIX` 로 둔다 |
| 포괄 위임 주문 (한도 · 품목 · 주기 위임, 패스키 위임장) | 주문은 건별 승인만 |
