# AI 규칙

AI 작업(LangGraph 그래프 · 모델 호출 · 도구 · 프롬프트 · 수요 예측)을 만들 때 지킬 규칙입니다. 구성 요소와 Spring · Python 경계는 [아키텍처](architecture.md), 발주 · 쿠폰 · 메뉴의 업무 규칙은 [도메인 규칙](domain.md)에 있습니다.

> **AI 흐름은 Python · LangGraph로 만듭니다.** 아직 구현 전입니다. 백엔드의 `ai/` 패키지와 Spring AI 의존성 · 설정은 비어 있는 틀로만 남아 있습니다. 같은 업무의 AI 호출을 Java와 Python 양쪽에 만들지 않습니다.

## 기본 원칙

| 원칙 | 내용 |
|---|---|
| 숫자는 서버가 | 수량 · 금액 · 마진 · 할인 부담 계산과 권한 · 승인 · 최종 조건 검증은 Spring이 한다. AI는 해석 · 후보 탐색 · 구조화된 계획 · 허용된 도구 선택 · 설명을 맡는다 |
| AI 답을 믿지 않는다 | 구조화 출력(Pydantic 모델) 변환 뒤에도 ID · 필수값 · 단위 · 수치 · 업무 조건을 검증한다. 검증에 실패한 결과는 승인 가능한 제안으로 저장하거나 실행하지 않는다 |
| AI는 실패할 수 있다 | 업무별로 실패를 나누고 기본 조회 · 수동 처리 경로를 유지한다. AI가 실패하면 임의의 수치 · 계획으로 외부 실행하지 않는다 |
| 한도를 둔다 | 탐색 · 재조정 · 재시도에 횟수 · 시간 · 비용 한도를 둔다. 반복 한도와 실패 경로는 코드에 두고 모델 호출을 무한 반복하지 않는다 |
| 필요한 것만 부른다 | 버튼 · 이벤트로 업무가 정해져 있으면 해당 그래프로 바로 연결한다. 자연어 요청을 지원할 때만 의도 해석을 추가한다. 매번 모든 업무를 실행하지 않는다 |
| 업무 표를 직접 바꾸지 않는다 | Python은 Spring 내부 API로만 데이터를 읽고 쓴다 |

## 기능별 흐름

| 기능 | 처리 흐름 | 끝나는 곳 |
|---|---|---|
| 운영 분석 | 데이터 품질 확인 → 매출 · 재고 · 예측 조회 → 필요한 분석 → 제안 충돌 검증 → 요약 | 요약은 승인 없이 표시. 발주 · 쿠폰을 자동 실행하지 않는다 |
| 발주 제안 | 필요량 계산 → 주 거래처 확인 → 조건부 대안 탐색 → 비용 · 배송 조건 검증 → 제안 저장 | 검증된 제안만 저장. 실패 · 미완성 결과는 승인할 수 없다 |
| 발주 실행 | 승인 확인 → 기존 주문 확인 → 주문 준비 → 실제 조건 대조 → 주문 → 결과 확인 | 인증이 필요하면 중단 · 재개. 결과가 불명확하면 `CHECKING` |
| 쿠폰 제안 | 조건 생성 → 손익 · 예산 · 재고 검증 → 제한된 수정 → 제안 저장 | 승인 뒤 별도 실행 작업에서 POS 지원 범위를 다시 확인 |
| 메뉴 · 레시피 | 품목 조회 → 초안 생성 → 품목 · 단위 · 원가 검증 → 미리보기 | 사용자가 추가/저장을 고르면 Spring이 다시 검증 · 저장 |

- 발주 · 쿠폰은 **제안 생성과 승인 후 실행을 별도 작업**으로 관리한다. 작업 ID와 graph thread를 따로 쓴다.
- 노드 상태에는 업무에 필요한 정보만 넣는다. 모든 상태를 대화 메시지 목록 하나에 쌓지 않는다.
- 조회 노드는 서로 독립인 것이 확인됐을 때만 병렬로 실행한다.
- 업무별로 입력 모델 · 출력 계획 모델 · 허용 도구를 나눈다.

## 공통 작업 순서

`요청 / 정기 실행 / 데이터 변경 → 권한 · 데이터 품질 확인 → 예측 · 계산 → 업무 그래프 → 제안 검증 · 충돌 조정 → 사용자 판단 → 실행 전 재검증 → 실행 · 결과 확인 → 후속 분석`

1. 매장 · 분석 기간 · 데이터 기준 시각 · 사용자 조건을 먼저 고정한다. 동기화 실패 · 미수신을 실제 0으로 처리하지 않는다. 부족한 데이터는 해당 업무의 보완 경로로 연결한다.
2. 제안끼리 재고 · 예산 · 기간 충돌이 없는지 확인한다 ([도메인 규칙 운영 분석](domain.md#운영-분석)).
3. 승인 · 인증 대기는 상태를 저장하고 멈춘다. 이벤트가 오면 그 업무만 재개한다. 긴 DB 트랜잭션이나 모델 호출을 붙잡은 채로 사용자 응답을 기다리지 않는다.

## 도구 권한 · 승인

| 작업 | 허용 조건 |
|---|---|
| 조회 · 분석 · 상품 탐색 | 인증된 사용자 · 매장 권한 안에서 승인 전에도 가능. 주문 · POS 등록 도구와 분리한다 |
| 발주 · 쿠폰 외부 실행 | 그 제안 버전에 대한 유효한 승인이 있고, 현재 실행 조건 검증을 통과했을 때만 |
| 메뉴 · 레시피 앱 저장 | 사용자의 추가/저장 선택 + 서버 검증. 별도 승인 대기를 만들지 않는다 |
| 로그인 · 결제 추가 인증 | 사용자에게 제어를 넘기고 에이전트를 멈춘다. 조건이 그대로면 구매 승인을 다시 요구하지 않는다 |

- `memberId` · `storeId` 는 Spring이 고정한다. LLM 출력이나 요청 본문이 권한 대상을 정하지 못하게 한다. 백그라운드에서 재개할 때도 소유권 · 연결 상태 · 실행 권한을 다시 확인한다.
- 발주는 판매자 · 상품 · 옵션 · 수량 · 최종 금액 · 배송 조건을, 쿠폰은 대상 · 할인 · 기간 · 한도를 승인 범위와 비교한다.
- 승인된 계획과 `approved_scope` 를 덮어쓰지 않는다. 범위가 바뀌면 새 제안 버전으로 다시 승인받는다. 이전 버전의 실행 결과도 확인해 중복 실행을 막는다.
- 외부 페이지 · 검색 결과는 데이터로만 다룬다. 시스템 지시나 사용자 승인으로 해석하지 않는다. 권한이나 도구 범위를 넓히지도 않는다.
- 최종 주문은 일반 클릭 명령과 따로 구분된 명령으로만 수행한다. 이 명령은 Spring이 현재 조건 · 승인 범위 · 실행 ID를 검증한 뒤 발급한다.

## 상태 저장 · 재개

- 업무 상태와 승인 기록의 기준은 **Spring 업무 DB**다. 작업 진행은 Python 작업 등록부, 단계 · 중간 결과는 LangGraph 체크포인트에 둔다 ([아키텍처 상태 저장 위치](architecture.md#상태-저장-위치)).
- 승인 전 생성 정보는 `suggestion.generation_context`, 최종 제안 · 근거는 `payload` · `evidence`, 승인 후 외부 실행 진행은 `execution.runtime_context` 에 나눠 담는다 ([DB 규칙](db.md#발주--결제--제안--실행)).
- context에는 **공통 필드 + 업무별 필드**를 검증된 모델로 정의한다. 대상은 작업 단계 · 작업 ID · 기준 시각 · 재시도 · 만료 · 재개 정보이고, 키는 camelCase다. 임의 구조나 인증 원문을 넣지 않는다.
- 같은 업무 실행은 원자적으로 선점하고 중복 이벤트를 막는다. 내부 `idempotency_key` 만으로는 쇼핑몰 쪽 중복 주문까지 막을 수 없다.
- `interrupt()` 로 재개하면 그 노드의 앞부분이 다시 실행될 수 있다. 그래서 주문 전송 · 대기 · 결과 조회는 별도 노드로 나눈다.
- 체크포인트를 복원한다고 실행기 브라우저 상태가 돌아오거나 중복 주문이 막히지 않는다. 재개할 때는 저장된 단계 · 승인 버전 · 실행기 기록 · 외부 주문 내역 · 현재 조건을 대조하고 미완료 작업만 이어간다.
- 주문 직후 응답이 끊기면 실패로 단정하지 않는다. 기존 주문 · 결제 결과부터 확인한다.
- 사용자의 '인증 완료' 버튼은 신호로만 받는다. 실제 로그인 상태 · 주문 내역 · 현재 조건을 다시 확인한 뒤 진행한다.
- 오래된 명령은 재연결 직후 바로 실행하지 않는다. 승인 · 기한 · 실제 주문 상태부터 확인한다.
- 중단된 작업은 호환되는 그래프 버전으로 재개한다.

## 인증 · 입력 데이터

- 쿠팡 로그인 · 세션 보관 · 추가 인증 방식은 **미정**이다 ([아키텍처 미정 사항](architecture.md#미정-사항)). 서버 흐름에는 인증 필요 · 사용자 개입 · 재개 접점만 만든다.
- 휴대폰 앱의 로그인 상태가 실행기와 자동으로 공유된다고 가정하지 않는다.
- 자체 쇼핑몰 비밀번호 · 카드번호 보관 기능은 만들지 않는다. 쇼핑몰에 등록된 결제수단을 쓴다.
- 추가 인증 중에는 에이전트 조작 · 민감 화면 수집 · 모델 전달 · 추적을 멈추고 사용자에게 제어를 넘긴다.
- LLM에는 필요한 집계값 · 상품 정보 · 재료 · 레시피 · 공개 검색 근거만 최소한으로 보낸다. 서버 AI가 페이지를 판단해야 할 때도 필요한 상품 정보만 추출 · 마스킹해서 보낸다.
- 이름 · 전화번호 · 사업자번호 · 실제 배송지 · 비밀번호 · 토큰 · 쿠키 · 인증번호 · 결제 인증값을 프롬프트 · 로그 · 체크포인트 · `payload` · `evidence` · context · LangSmith에 넣지 않는다. 실행에 필요한 배송지 등은 보호된 서버 컨텍스트에서 실행기로만 전달한다.

## 수요 예측

- `ml/` 에서 학습 · 검증한 모델 버전을 FastAPI가 불러와 예측한다. 요청마다 학습하지 않는다.
- 응답에는 예측 기간 · 수량 · 모델 버전 · 데이터 기준 시각을 넣는다. Spring이 검증 · 저장하고 발주량 계산에 쓴다.

## 프롬프트 · 추적 · 비용

- 프롬프트는 업무별 파일로 나눈다. 코드에 긴 프롬프트 문자열을 넣지 않는다. 출력 형식은 입출력 모델 계약과 맞춘다.
- LangSmith는 AI 호출 · 도구 사용 · 오류 · 지연 · 사용량 · 품질 평가에 쓴다. 업무 원본 · 승인 · 주문 상태를 저장하는 곳으로 쓰지 않는다. 업무 기록과는 `langsmith_trace_id` 로 연결한다.
- 추적에 넣는 프롬프트 · 응답 · 도구 결과는 민감정보를 지운 뒤 보낸다. 인증 구간은 빼고, 연결이 실제로 추적되는지 확인한다.
- 개발 중 기본 모델은 기존 설정 `claude-haiku-5-5` 를 따른다. 모델 ID · 라이브러리 버전은 실제 연결을 확인한 뒤 lock에 고정한다. 문서를 고친다고 버전을 바꾸지 않는다.
- 연결 확인 API는 `/api/ping` 에 넣지 않는다.
- 테스트에서는 실제 모델을 호출하지 않는다 (과금). 가짜 모델 · 가짜 실행기를 쓴다.

## AI 기능 검증 기준

[AGENTS.md 테스트 규칙](../../AGENTS.md#5-테스트-규칙)에 더해, AI 작업은 아래 경우를 테스트로 확인합니다.

- 주 거래처가 적합하면 대안을 찾지 않는다 / 불가가 확인됐을 때만 찾는다 / 로그인 오류와 품절을 구분한다.
- 생성 실패 · 데이터 부족 초안은 승인할 수 없다 / 다른 매장 · 다른 버전 승인을 막는다 / 조건이 바뀌면 다시 승인받는다.
- 쿠폰 손익 · 재고 충돌 검증 / POS 중복 등록 방지 / 메뉴 추가 선택과 POS 반영을 구분한다.
- 인증 대기 · 서버 재시작 후 재개 / 주문 응답 유실 · 부분 성공일 때 중복 실행을 막는다.
- 단위 환산 · 포장 수량 · 금액 계산 / 주문 · 결제 · 입고 분리 / 미결제 금액 · 시각 NULL 규칙.
- 인증정보가 로그 · 체크포인트 · 추적에 남지 않는다.
- Java record와 Python 모델의 JSON 모양이 같다 (계약 테스트). 금액 · 수량은 Decimal, 시간은 offset이 붙은 ISO 8601.
