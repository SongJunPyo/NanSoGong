# 프론트엔드 규칙

React PWA(`frontend/`) 코드 규칙입니다. JavaScript · JSX를 쓰고 TypeScript는 쓰지 않습니다. 구조의 기준은 [WONIT-A/07_cicd](https://github.com/WONIT-A/07_cicd)의 `frontend/src/` (api · components · hooks · utils) 입니다.

## 폴더 구조

```
frontend/src/
├── App.jsx · AppRouter.jsx · routes.js
├── api/           서버 호출은 여기에만. client.js의 request() 하나 + 도메인별 파일
├── components/
│   ├── ui/        shadcn/ui 부품 (공용)
│   ├── common/    하단 탭바 · 헤더 · 로딩 · 에러 표시
│   └── <도메인>/   XxxPage.jsx …
├── features/      (옮기는 중) 도메인별 화면 · mock.js · queries.js
├── hooks/         useXxx (TanStack Query 훅 포함)
├── store/         Zustand (로그인 · 선택 매장)
├── utils/         format.js (금액 · 날짜)
└── lib/utils.js   shadcn용 (건드리지 않는다)
```

- 지금은 `features/<도메인>/` 과 `components/<도메인>/` 이 함께 있다. 목표는 위의 종류별 구조(`api` · `components` · `hooks`)다. 새 화면을 어디에 둘지 애매하면 같은 도메인의 기존 파일 위치를 따른다.
- 화면 목록과 주소는 `src/routes.js` 의 `ROUTES` 에서 관리한다. 새 화면은 여기에 한 줄을 추가한다.

## 코드 규칙

| 규칙 | 이유 |
|---|---|
| **컴포넌트에서 `fetch` 를 직접 부르지 않는다.** 항상 `api/<도메인>.js` → `request()` | 토큰 · 에러 처리를 한 곳에서만 고치기 위해 |
| 서버 데이터는 TanStack Query. **`queryKey` 에 `storeId` 를 꼭 넣는다** | 매장을 바꿨을 때 다른 매장 데이터가 보이는 사고를 막는다 |
| Access는 메모리(Zustand), Refresh는 서버 HttpOnly 쿠키에만 둔다. **`localStorage` · `sessionStorage` 에 인증 토큰 저장 금지** | XSS로 토큰이 털리지 않게 |
| 에러는 `err.message` 를 그대로 보여 준다 | 서버 `ErrorResponse.message` 가 사용자용 문구다 |
| **모바일 우선**: 폭 360px에서 먼저 확인한다. 스타일은 Tailwind 클래스, 공통 부품은 shadcn/ui | PWA · 사장님 휴대폰 |
| 금액 · 날짜 표시는 `utils/format.js` 를 쓴다 | `toLocaleString` 을 여기저기 흩뿌리지 않기 위해 |
| 상태 코드(`NEEDS_FIX` 등)의 한글 표시는 프론트에서 바꾼다 | 서버 · DB는 영어 코드만 쓴다 |

- 백엔드 API가 아직 없으면 **합의한 JSON 예시를 return하는 가짜 함수**로 `api/<도메인>.js` 를 먼저 만든다. API가 생기면 `request()` 로 바꾼다.
- shadcn 부품을 추가(`npx shadcn@latest add …`)하면 사용자에게 알리고 PR 설명에 따로 적는다.
- AI 진행 상태(진행 중 · 인증 필요 · 재승인 필요 · 결과 확인 중 · 완료)와 실행기 연결 상태는 서버가 준 상태 코드대로 보여 준다. 화면에서 상태를 추측해 만들지 않는다.
- 정해지지 않은 화면(실행기 연결 · 인증 안내 등)은 목업으로 만들고 범위 밖 기능은 [도메인 규칙](domain.md#현재-범위-밖)을 따른다.

## 회원가입의 사업자 진위확인

- 사업자 확인 버튼은 `api/auth.js` → `client.js`의 `request()`로 [백엔드 진위확인 API](backend.md#국세청-사업자-진위확인)를 호출한다. 사업자번호·대표자명·개업일자만 보내고 상호·인증키는 보내지 않는다.
- 조회의 진행·오류·결과는 TanStack Query의 `useMutation`으로 관리한다. 가입 전이라 매장 ID가 없으며 자동 재시도와 화면 이탈 후 결과 캐시는 사용하지 않는다.
- 진위확인 실패·잘못된 응답을 Mock 성공이나 상태조회로 대체하지 않는다. 휴업·폐업·진위 불일치는 등록 목록에 추가하지 않는다. 입력을 수정하면 이전 확인 결과를 지운다.
- 정보 일치·영업 중인 결과만 등록 목록에 추가한다. 최종 가입에는 사업자 입력을 보내고 서버가 다시 확인한다. 클라이언트의 사업자 확인 결과·가짜 증명을 가입 권한으로 보내지 않는다.
- 아이디 확인·휴대전화 인증 요청/확인·가입·로그인·내 정보/매장 조회·기본정보 저장은 실제 서버를 호출한다. 휴대전화의 개발용 인증 제한은 [가입 계약](backend.md#회원가입--로그인--매장-저장)을 화면에 표시한다.
- 가입 초안·인증 증명·JWT는 메모리에만 둔다. 가입 성공 시 초안을 지운다. 새로고침 시 세션을 복원하고 DB의 회원·매장 정보를 다시 읽는다. 로그인 유지·로그아웃은 [세션 처리](#로그인-유지--로그아웃)를 따른다.
- `createAuthMock`의 번호별 예시는 순수 Mock 테스트에서만 사용한다. 화면의 진위확인은 항상 서버를 사용한다. 실제 국세청과 목업 중 어느 쪽에 연결되는지는 백엔드 설정으로 정한다.

## 비밀번호 재설정

- `/find-password`에서 아이디·가입 전화번호 → 인증번호 → 새 비밀번호·확인 순서로 실제 서버를 호출한다. API·MOCK 제한과 REAL의 일반 계정 지원은 [백엔드 계약](backend.md#일반-계정-비밀번호-재설정)을 따른다.
- capabilities 응답으로 개발용/실제 SMS 준비 상태를 구분한다. 준비되지 않은 일반 계정 재설정은 비활성화하고 이유를 안내한다. 실제 발송되지 않은 문자를 발송했다고 표시하지 않는다. 데모 데이터가 없는 환경에서는 예시 계정도 인증할 수 없다.
- 조회 요청은 존재 여부를 드러내지 않는 같은 문구로 안내한다. 진행·오류는 `useMutation`으로 처리하며 자동 재시도·화면 이탈 후 캐시는 사용하지 않는다.
- 인증번호·재설정 권한·비밀번호는 컴포넌트 메모리에만 둔다. 만료 시 새 비밀번호 저장을 막고 처음부터 다시 진행한다. 처음으로 돌아가면 이전 입력·증명을 지운다.
- 성공 시 로그인·선택 매장·가입 초안·쿼리 캐시를 지우고 로그인 화면에 완료 문구를 표시한다. 비밀번호 재설정 요청에는 로그인 JWT를 보내지 않는다.

## 회원정보 조회 · 수정

- 설정의 회원정보는 `GET /api/me`로 읽고 `PATCH /api/me`로 저장한다. 요청·응답은 [백엔드 계약](backend.md#회원정보-조회--수정)을 따른다. 예시 회원정보나 가짜 저장 성공으로 대체하지 않는다.
- 회원정보 쿼리는 매장이 아닌 로그인 회원 번호로 분리한다. 아이디·전화번호는 읽기 전용이며 이름을 수정할 수 있다. 전화번호 변경은 별도 폼에서 현재 비밀번호 확인 → 새 번호 SMS 확인 → DB 저장 순서로 진행한다. 발송 실패·인증 만료·저장 실패 시 완료를 표시하지 않는다. 재인증 시 이전 입력·증명을 지운다.
- 비밀번호 변경을 선택하면 현재 비밀번호·새 비밀번호·확인을 입력한다. 입력은 컴포넌트 메모리에만 두며 취소하면 지운다. 이름과 비밀번호를 함께 보내면 서버가 한 번에 검증·저장한다.
- 저장 중에는 중복 요청을 막는다. 실패하면 서버의 `err.message`와 입력값을 유지한다. 성공 후에만 이름의 쿼리 캐시와 로그인 회원정보를 갱신하고 성공을 안내한다. 이전 조회 응답이 늦게 도착해 저장 결과를 덮어쓰지 않도록 해당 조회를 취소한다.
- 요청 중 계정이나 세션이 바뀌면 이전 응답으로 현재 계정 상태를 바꾸지 않는다. 비밀번호 변경 성공 시에는 로그인·선택 매장·가입 초안·쿼리 캐시를 지우고 재로그인을 안내한다. Access 갱신은 같은 세션으로 처리하고 이전 계정 응답은 반영하지 않는다.

## 로그인 유지 · 로그아웃

- API·쿠키·CSRF 정책은 [백엔드 계약](backend.md#로그인-유지--서버-로그아웃)을 따른다. 로그인 상태 유지 체크박스의 값을 실제 로그인 요청에 보낸다.
- 보호 화면·로그인 화면은 처음 로드할 때 Refresh 쿠키로 세션을 복원하고 회원·매장을 다시 조회한다. 복원 중에는 보호 화면을 렌더하지 않는다. 인증 만료는 로그인으로 이동하고 네트워크·서버 오류는 재시도 경로를 표시한다. 저장된 선택 매장은 내 매장 목록에 있을 때만 유지한다.
- client.js의 전송 계층이 만료된 요청을 한 번만 갱신·재시도한다. 한 탭에서는 같은 Promise, 지원 브라우저의 여러 탭에서는 Web Locks로 CSRF 조회와 쿠키 변경을 직렬화한다. Web Locks가 없는 환경의 동시 사용은 서버의 엄격한 재사용 탐지로 재로그인이 필요할 수 있다. 완화된 재사용 허용 기간을 임의로 두지 않는다.
- CSRF 토큰은 HttpOnly Refresh를 직접 읽지 않고 서버에서 요청 직전에 가져온다. 인증·재설정 API에 오래된 Bearer를 보내지 않는다. 세션 세대가 바뀌면 이전 성공·실패·갱신 응답을 반영하지 않는다.
- 로그아웃은 서버 요청을 수행한 뒤 메모리·캐시·선택 매장·가입 초안을 지운다. 서버 종료 확인이 실패해도 로컬 정보는 지우지만 오류 문구를 안내하며 서버 로그아웃 성공으로 표시하지 않는다. 비밀번호 변경·재설정 후에도 재로그인을 안내한다.
- 탈퇴 실행은 정책 미정으로 비활성화한다. 프론트에서 탈퇴 성공이나 데이터 삭제를 임의로 흉내내지 않는다.

## 확인

- `cd frontend && npm run lint && npm run build`
- 패키지 설치는 `npm ci`. lock 파일을 바꿀 때만 `npm install` 후 lock을 커밋한다.
